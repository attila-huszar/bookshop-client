# Frontend architecture

This document covers the React application, client state, API access, routing, checkout interface, translations, and tests. Database adapters, API contracts, Stripe webhooks, email delivery, and container operations are documented in the [backend architecture](https://github.com/attila-huszar/bookshop-server/blob/HEAD/docs/architecture.md).

## Modules and components

Reusable client components expose their public API through a folder-level `index.ts`, for example `@/components/Button` exports `Button` and `IconButton`. Pages, components, and hooks use these folder imports; there is no global components barrel. A component's own implementation uses relative file imports within its folder to avoid importing its own entrypoint. Header and Footer keep their private internals behind their public entrypoints.

Client runtime imports point to the module that owns the symbol: API functions, Redux slices/thunks/selectors, hooks, helpers, constants, styles, validation schemas, and the logger have direct imports instead of broad barrels. Route constants come from `src/routes/route.ts`; the router comes from `src/routes/Routes.ts`. This keeps route constants separate from router initialization and lets tests mock the actual module used by each caller. Component folder entrypoints, local component groups, the type exports, and SVG aliases remain useful public APIs. `src/i18n/index.ts` implements initialization and is not a re-export barrel.

## Server data and local state

RTK Query owns books, author references, news, account orders, CMS data, and payment HTTP requests. Page hooks own fetching, subscriptions, loading, and errors; there are no catalogue, orders, or CMS preload loaders. Orders and CMS lists refresh on mount, while public catalogue queries use their freshness intervals. The catalogue uses `currentData` so changing page or applied filters hides the previous result until the new query resolves, while refreshing the same cached page keeps it visible. Pagination receives the total from that page's response. The homepage combines only featured-book errors through a focused selector, so catalogue and homepage failures remain independent. Other memoized selectors derive catalogue query arguments and combine session/profile state; local workflow fields use direct selections. CMS mutations invalidate public and CMS query tags together. Thin thunk adapters support Search and form dispatch contracts but do not own entity caches; mutation adapters dispose of their result entries.

The Ky-to-RTK Query adapter is a private `baseQuery` in `src/store/api/bookshopApi.ts`. Endpoints opt into token attachment and shared refresh with `withAuth: true`; the flag selects `authRequest` and does not assert that a user is logged in. Guest checkout endpoints also use this client and set `credentials: 'include'` separately for payment cookies. Public endpoints use `baseRequest`. Plain API calls remain in `src/api` for workflows that do not need RTK Query caching.

`bookshopApi.ts` creates the shared API with an empty endpoint definition. The books, authors, users, orders, terms, news, and payments modules in `src/store/api` add their queries and mutations with `injectEndpoints`. The store registers only the shared reducer and middleware, so cache tags still invalidate queries across domains. Domain modules import the shared API; the shared API does not import domain modules. Each domain exports its API object and generated hooks. Importing that domain registers its definitions before use. Modules used by selectors and basket reads load during startup; other modules can follow their route imports.

Shared cache resets use `bookshopApi.util`. Imperative query calls and selectors use the owning domain's `.endpoints`; query-data utilities such as `upsertQueryData` use its `.util`. Domain API objects retain endpoint-specific argument and result types without separate shorthand exports or an aggregator that imports every domain into the base module. Components use generated hooks; book prefetching calls `booksApi.usePrefetch` directly. API integration coverage remains in `bookshopApi.test.ts`, including invalidation of cached books after an author mutation from another module.

The remaining Redux slices own cart intent, authentication/session state, checkout workflow state, and book pagination/filter UI. Filter submission uses `buildBookCriteria` in `src/store/api/booksQuery.ts` to normalize the initial and submitted ranges once. Cleared ranges and bounds covering the initial range, including outward-rounded prices, are omitted. With no effective filters, criteria stay `undefined`, so submitting the full range reuses the unfiltered query cache entry. Draft filters retain the slider range arrays; applied filters store only effective criteria using API query parameter names. Price and year share one range comparison, and query serialization handles scalar values and repeated genres uniformly. Query responses are immutable; Search copies results before merging them. Logout, login transitions, and lost refresh sessions reset the query cache. Cache data and payment secrets are not persisted to browser storage. See [RTK Query cache invalidation](https://redux-toolkit.js.org/rtk-query/usage/automated-refetching).

Cache settings use RTK Query's native options where they apply. Domain endpoints set `keepUnusedDataFor`, which controls retention after the last subscription ends. Page hooks use `refetchOnMountOrArgChange` to refresh old results on subscription, and prefetch hooks use `ifOlderThan` to refresh old results on intent. All durations are in seconds, using the shared `CacheTime` enum in the client's `src/constants/cacheTimes.ts`. Its members describe durations rather than domain policies; each endpoint or hook independently chooses its retention or freshness threshold. See [cache behavior](https://redux-toolkit.js.org/rtk-query/usage/cache-behavior) and [prefetching](https://redux-toolkit.js.org/rtk-query/usage/prefetching).

## Routing, startup, and cart recovery

The root `appLoader` restores the cookie session before pages mount, then restores validated cart IDs and quantities from browser storage without fetching books. The shared client type for this basket intent is `CartItem`. A strict Yup schema validates the saved cart as a whole; invalid data restores an empty cart without coercing values or salvaging individual rows. Saved carts, order forms, and explicit cart quantity updates reuse the same item-quantity schema. `shouldRevalidate: () => false` prevents navigation from repeating startup. Cart subscribes to canonical per-book RTK Query entries through `useCart`; cached and pending reads are shared, and server responses never replace cart intent. Failed reads can be retried without discarding the basket. Forced price recovery waits for older in-flight reads before fetching fresh prices, bypassing stale cache entries. The root and Checkout share `bootstrapSession` in `src/services/session.ts`: concurrent calls share token refresh and count a failed guest attempt once toward backoff. The live protected-layout guard subscribes to the profile, waits before mounting private pages, offers retry on profile failure, and checks the current admin role. App keeps a profile subscription for the shared header. The only other loaders are Cart's immediate active-checkout redirect and Checkout's payment recovery. Product reads and validates its positive decimal safe-integer ID directly from the URL and skips invalid queries.

Targeted public prefetching uses RTK Query's `usePrefetch` on hover or keyboard focus. Book cards, featured book links, and search results warm only the selected book. The Shop menu link and homepage Shop button warm the current catalogue query and filter options. Pagination warms only the indicated valid page with the current applied filters and page size. Freshness thresholds prevent repeat requests, and page hooks reuse those same cache entries. Rendering a link alone does not prefetch; private orders and CMS data are fetched only after the route guard allows their pages to mount.

## Authentication flows

Login and registration label their inputs, lock editable fields while submitting, and ignore completion toasts/navigation after leaving the page. Completion messages use the language active when the response arrives. Registration country detection fills only an untouched country field; it does not reinitialize the form or replace an explicit selection. Email verification and reset-token previews each share concurrent POSTs for the same token in `src/api/users.ts`. Pending entries are removed on success or failure, so later attempts validate with the server again. Page effects run normally and ignore results after navigation; this also lets a real remount join an existing request. Reset-link forms reset their form state when the URL token changes and ignore late password-submission results after navigation. Strict Mode stays enabled. Missing reset links use a stable toast ID so effect replay updates the same notification. Protected routes react to session expiry and role changes without cached loader authorization. Logout waits for cookie clearing before navigating away; a failure keeps the session and menu available for retry.

## Checkout and payment recovery

Checkout gives a Stripe return's payment ID precedence over an older stored checkout and removes Stripe IDs/secrets from the URL with history replacement before retrieval. `paymentsApi` injects create, retrieve, and cancel endpoints into the shared API; retrieval retains only the needed fields and has no unused-cache retention. `src/services/checkout.ts` coordinates these requests and is the sole writer of the safe payment ID and accepted workflow transitions. The payment slice holds a minimal in-memory session, phase, operation ID, and coded error. Ready responses pass a strict `paymentSessionSchema` before their fields enter state or storage. After asynchronous work, the coordinator checks operation identity and the stored checkout ID before committing state or storage. Resets invalidate pending results, so old creates, reads, failures, and cancellations cannot replace a newer checkout. The cart persistence listener stores IDs/quantities and resets checkout only when intent changes; it does not handle payment request results. Payment mutations dispose of their RTK result entries after completion. The navigation signal aborts its owned retrieval request; a later restore waits for an earlier shared read before issuing its own request. Aborted reads retain the safe ID without a visible error, unavailable sessions clear it, and transient failures leave it available for retry. Identical creation retries retain their idempotency key until the current attempt succeeds or the server reports that checkout ended; changed requests or an explicit reset start a fresh attempt. Price conflicts refresh canonical book prices once without submitting another payment. Stripe confirmation, versioned terms acceptance, and status polling stay in their existing UI hooks. Signed-in checkout waits for the profile before mounting Stripe forms with address defaults; guest checkout and Stripe return results do not wait for a profile. Payment tokens remain in memory and guest cookie behavior is unchanged.

Shared totals, amount formatting, payment status rules/formatting, and Stripe error formatting live in `src/helpers/checkout.ts`; payment status text selection and animations live in `PaymentStatus.tsx`. `usePaymentStatus` exposes a tagged state for Stripe statuses, initial checking, retries, failures, and timeout, with metadata only on the relevant variant. It retains the final result after session cleanup, resets for a different payment token, and ignores late responses from stopped polling runs. Polling uses at most three requests with 5- and 10-second delays and a 30-second absolute deadline; retry metadata names the next request and total attempt limit. Status and error details stay untranslated, so changing language updates the display without restarting payment checks. Stripe-provided card/validation messages remain preferred over translated fallbacks.

The server calculates authoritative prices and persists immutable order snapshots. The return page's status display does not mark an order paid; Stripe webhooks and reconciliation do that. See the [backend checkout flow](https://github.com/attila-huszar/bookshop-server/blob/HEAD/docs/architecture.md#custom-checkout) for ownership, access rules, identifiers, and database guarantees.

## Terms and CMS

The admin CMS menu includes **Terms and Conditions** and a return-to-home action. It uses the storefront's dropdown on desktop and drawer on mobile. The terms action opens a modal with EN/HU tabs where admins enter plain text and choose **Save and publish**. A publication dropdown shows localized dates with the current version marked. Selecting an older publication loads its immutable document through the version endpoint. Each selection retains its own unsaved edits for the lifetime of the editor; browsing history never changes the current publication. Publishing edited historical text creates a new revision. RTK Query owns current terms, history, and archive queries; publishing invalidates current terms and history while immutable archives remain cached.

The history response's `canDelete` flag controls a bin button between Cancel and Publish. It is disabled for any version already accepted by an order. Successful deletion closes the editor and invalidates current terms, history, checkout references, and the deleted archive's cache entry. Rejected deletion refreshes history without discarding drafts. Deleting the last publication leaves terms unavailable and blocks payment submission.

The payment form starts with an unchecked, required terms checkbox and shows the persisted order items and payable amount. English wording is **Order with obligation to pay**; Hungarian uses **Fizetési kötelezettséggel járó megrendelés**. Refreshing checkout or changing language requires checking the box again. Unpublished terms or a failed terms/acceptance request prevents payment submission in the client.

Checkout loads the terms reference and persisted order summary from `GET /api/payments/:paymentId/terms`. It displays that version's stored acceptance statement in the selected language; the statement is versioned legal data, separate from interface translation JSON. The client saves `{ accepted: true, version, language }` to the same payment terms route and waits for acceptance before calling Stripe confirmation. The server owns validation and the acceptance record.

The public `/terms` page shows the current document, while `/terms/:version` shows the exact archived text in the selected interface language. The page shows the publication date and one Download button below the terms text, following the language selected in the shared header. Download requests select the same version and language; filenames use the publication date in Europe/Budapest, for example `terms-2026-10-27-hu.txt`. Raw version identifiers remain in archive/download URLs and are not displayed in the page body. Customers can download without signing in; browser printing remains supported. The footer and checkout link to these pages.

The checkbox and payment-obligation wording cover only part of the checkout requirements. The [backend terms documentation](https://github.com/attila-huszar/bookshop-server/blob/HEAD/docs/architecture.md#terms-publication-and-acceptance) records publication/acceptance guarantees and the remaining merchant-specific legal and durable-confirmation requirements.

CMS order Add is disabled. Customer/shipping details remain editable; status, paid time, totals, currency, and items are read-only, with the server enforcing the same allowlist. There is no CMS “mark paid” action.

The CMS reads one list per entity and filters active/deleted orders and users locally. Their deletion is reversible; catalogue deletion is permanent and is named **Hard delete**. The Orders tab requests email history only when expanded and supplies the order's exact `paymentId`. Recipient/type/status filters stay within that order. Email summaries omit bodies, account links, and lease tokens, and the interface offers no resend/delete actions.

## Interface languages

The client initializes `i18next`, `react-i18next`, and `i18next-http-backend` from `src/i18n/index.ts`. UI resources are in `public/locales/en/translation.json` and `public/locales/hu/translation.json`. Vite copies them into the output as separate files; production code loads them over HTTP instead of bundling their contents into JavaScript. i18next's built-in `preload: ['en', 'hu']` loads both into memory at startup. Language detection still determines which language is displayed, with English as the fallback. Switching to a successfully preloaded language needs no additional HTTP request. Runtime requests use `cache: 'no-cache'` to revalidate cached translations when loading them.

An app-level Suspense boundary in `src/main.tsx` renders nothing until translations initialize. `App` checks translation readiness through `useTranslation()` before rendering its children, so page loading boundaries cannot reveal part of the interface early. The footer and language selector use ordinary translation hooks. Lazy pages retain their route loading boundaries. If Hungarian cannot load, startup falls back to English without overwriting a saved choice; initialization failures are reported through the client logger. The selector calls `i18n.changeLanguage` directly and saves an explicit preference only when the requested translation bundle is available. Loading failures use i18next's built-in fallback behavior; there is no custom backend reload or retry path. Keep the JSON keys consistent with the application when deploying these files independently. `src/i18n/i18next.d.ts` references both JSON resource shapes for TypeScript key and grammatical-context checking; that declaration produces no runtime import.

The storefront, navigation, account/authentication forms, cart, checkout, terms flow, and CMS use the same English/Hungarian interface resources. Shared actions and field labels live under `common`; the remaining objects follow feature order in both JSON files. Reuse complete messages and interpolate variable data instead of assembling English fragments. Navigation/filter descriptors store translation keys, while API paths, roles, payment statuses, and filter values keep their wire values. Ordinary interface text uses `t()` directly. Grammatical variants use i18next contexts: checkout requests `terms.title` with `context: 'accusative'`, which selects Hungarian `title_accusative` and falls back to the base title in English. Resource checks require matching base keys, interpolation placeholders, and embedded markup while allowing language-specific accusative variants. Decorative emojis stay out of translation JSON; payment-status prefixes are mapped alongside shared checkout constants and helpers in `src/helpers/checkout.ts` and rendered with `aria-hidden` alongside the translated message. The stored acceptance declaration remains unchanged. Yup message callbacks resolve the current language when validation runs; visible field errors are revalidated after a language change without resetting form values. `src/validation/locale.ts` supplies translated defaults for built-in Yup messages. Country names use `Intl.DisplayNames` in Hungarian without changing or refetching cached country data. Date/amount formatting follows the displayed language, and Stripe Elements receives the selected locale.

The wider account dropdown and mobile drawer include a language row showing the active language name and matching flag, using the same FlagCDN helper as country selection. Clicking the row switches between English and Hungarian and updates both the flag and label. Guests use one flag icon button between Login and Basket, with the flag following the selected language. The public terms page follows the header language selection. Both variants share loading/error handling and preference storage. An explicit choice is remembered in browser storage and overrides browser language detection. Without a valid saved preference, startup uses the first supported language in `navigator.languages`, mapping regional tags such as `hu-HU` to `hu` and `en-GB` to `en`. If the list is empty, it checks `navigator.language`; if no supported language is found, it uses English. Detection and loading fallbacks are not saved as explicit choices, so future visits can follow changed browser preferences. The document language always follows the active language.

The JSON resources contain interface wording. Actual legal terms are edited separately in the CMS; the app does not automatically translate legal text.

## API errors and logging

Client types describe API responses and commands, including author IDs when editing books. They do not expose internal database records. Application error codes are defined in `src/types/ApiError.ts` and match the server's thematic enums. API errors include a stable `code` and optional public validation details using native Zod issue codes. The [backend response and error contracts](https://github.com/attila-huszar/bookshop-server/blob/HEAD/docs/architecture.md#api-response-and-error-contracts) document the wire format and server-side response allowlists.

The client maps API/rule codes to existing translation keys in `src/helpers/errors.ts`, reusing shared field labels for validation details. Unknown codes and unrecognized HTTP response bodies use a translated fallback. `getErrorMessage` selects UI text; `toAppError` preserves API details and the original `cause` when rethrowing, without logging. Network and JSON parsing failures use translated fallback text; timeouts have a translated error code. Ky's `beforeError` hook logs final request failures once after retries, skips cancellations, and deduplicates errors propagated through auth retries. Log uploads use the shared transport without that hook to avoid recursive logging. RTK Query retains serializable codes/validation details; selectors pass them to alerts for translation during rendering, so switching language updates cached errors without a refetch. Checkout submission, cancellation, and terms publishing also retain API details for visible errors. Toasts use the language active when shown. Payment creation triggers cart price-conflict recovery only for `PRICE_CONFLICT`, preserving checkout retry/idempotency rules. React components use `useTranslation()` to subscribe to language changes; schemas, transport handlers, thunks, and request effects use the configured instance when they need the current language without a React subscription.

## Tests and development

Client tests use real application hooks and routing by default. `src/setupTests.tsx` provides browser shims, translation fixtures, notification mocks, and a disabled remote logger; it does not import the Redux store or replace application hooks globally. `Providers` in `src/testUtils.tsx` creates a fresh Redux store and `MemoryRouter` per mount and clears RTK Query state on unmount. Integration tests exercise those real dependencies; isolated tests declare the specific module mocks they need locally. Vitest clears mock calls and restores spies before each test through its configuration. Test utilities and environment setup are excluded from application coverage.

Run `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test:ci`, and `npm run build`. Client coverage includes route/session behavior, RTK Query invalidation and isolation, cart persistence, checkout recovery/idempotency, translation resources, and authentication forms. Backend database, Stripe webhook, email delivery, and provider smoke checks are covered in the backend architecture document.

Node.js runs Vite and the development, build, lint, and test tools; the deployed frontend consists of static browser assets. `.node-version` selects the Node 26 release line for CI and compatible build providers. The CI workflow uses `actions/checkout@v7`, `actions/setup-node@v7`, and the `ubuntu-24.04` runner. Development scripts start local Vite alongside the backend's Docker Compose stack; API/worker reload and container operations are described in the [backend development notes](https://github.com/attila-huszar/bookshop-server/blob/HEAD/docs/architecture.md#verification-and-production-follow-ups). Vite's development output stays in the local terminal; browser reports pass through the API into Loki with `source="frontend"`.
